# Pipeline Logging and Run Interpretation

## Purpose

This document explains how to read, interpret, and troubleshoot JSON pipeline run logs generated by the project orchestration scripts.

The goal is to make pipeline execution auditable and easy to diagnose.

This document applies to:

```text
Purchases pipeline
Inventory pipeline
Zenput safe wrapper
future orchestration scripts
```

Current implemented log folders:

```text
logs/purchases_pipeline_runs/
logs/inventory_pipeline_runs/
logs/zenput_pipeline_runs/
```

These logs are local execution artefacts.

They should not be committed.

Recommended `.gitignore` rule:

```gitignore
# Pipeline run logs
logs/
```

---

## Why Pipeline Logging Exists

Pipeline logging exists to answer:

```text
What pipeline ran?
When did it start?
When did it finish?
Did it run in dry-run mode?
Which steps executed?
Which steps were simulated?
Which steps succeeded?
Which steps failed?
Which steps were skipped?
How long did each step take?
Was the final required validation successful?
Was a safety gate triggered?
What run_id connects the console output to the JSON file?
```

The project uses JSON logs because they are:

```text
human-readable
machine-readable
easy to archive
easy to inspect after execution
easy to connect to future database run-log tables
```

# Common JSON Log Fields

Most pipeline logs include:

```text
run_id
pipeline_name
status
dry_run
started_at
finished_at
duration_seconds
total_steps
success
dry_run_steps
skipped
failed_or_error
required_failed_or_error
steps
```

Some fields vary by pipeline.

Purchases logs may not include every field that Inventory or Zenput logs include, depending on the current version of the script.

Inventory logs include:

```text
skipped
```

Zenput logs include additional safety and step metadata:

```text
execute
allow_legacy_writes
read_only
writes_database
writes_file
legacy
```

---

## Field: run_id

Example:

```text
run_id: 6e275bf6-ef2e-4944-a144-da646a9fabe5
```

Purpose:

```text
Unique identifier for one pipeline execution.
```

Use this value to connect:

```text
console output
JSON log filename
future database run-log record
future validation results
```

---

## Field: pipeline_name

Possible current values:

```text
purchases_pipeline
inventory_pipeline
zenput_pipeline
```

Purpose:

```text
Identifies which pipeline generated the log.
```

---

## Field: status

Possible values:

```text
COMPLETED
FAILED
```

Meaning:

```text
COMPLETED:
    No required step failed.

FAILED:
    At least one required step failed or a safety gate blocked execution.
```

Important:

```text
FAILED is not always bad.
```

For Zenput, a failed safety gate can be expected and correct when testing protection behaviour.

---

## Field: dry_run

Possible values:

```text
true
false
```

Meaning:

```text
true:
    Steps were simulated.
    Real ETL modules were not executed.
    No data writes should occur.

false:
    Steps may have executed for real, depending on the pipeline and flags.
```

---

## Field: duration_seconds

Purpose:

```text
Shows how long the full pipeline execution took.
```

Use this to identify:

```text
unexpectedly slow runs
step runtime growth over time
possible performance bottlenecks
```

---

## Field: total_steps

Purpose:

```text
Counts how many steps were part of the executed or simulated plan.
```

Examples:

```text
Purchases pipeline:
    total_steps: 10

Inventory base pipeline:
    total_steps: 7

Inventory extended pipeline with bridge reports:
    total_steps: 10

Zenput default dry-run:
    total_steps: 4

Zenput validation-only execution:
    total_steps: 2

Zenput safety gate block:
    total_steps: 1
```

---

## Field: success

Purpose:

```text
Counts steps that executed and returned SUCCESS.
```

Important:

```text
In dry-run mode, success may be 0.
```

Example:

```text
success: 0
dry_run: 4
PIPELINE RESULT: COMPLETED
```

This is valid if the run was intentionally simulated.

---

## Field: dry_run_steps

Purpose:

```text
Counts steps marked as DRY_RUN.
```

This should equal `total_steps` in a full dry-run, unless a safety gate or skip condition changes the plan.

---

## Field: skipped

Purpose:

```text
Counts steps intentionally skipped.
```

A skipped step is not necessarily a failure.

Common reasons:

```text
optional future module not present
configured skip flag
future validator included but not available
```

---

## Field: failed_or_error

Purpose:

```text
Counts all steps with FAILED or ERROR status.
```

This includes required and optional steps.

---

## Field: required_failed_or_error

Purpose:

```text
Counts failed or errored steps that are required.
```

This is the most important summary field.

Rule:

```text
If required_failed_or_error > 0, the pipeline result should be FAILED.
```

---

```text

```


---

## Step Status Values

Current status values:

```text
DRY_RUN
SUCCESS
FAILED
ERROR
SKIPPED
```

---

## DRY_RUN

Meaning:

```text
The step was simulated.
The module was not executed.
```

Valid for:

```text
safe planning
execution plan review
smoke tests
pipeline wrapper verification
```

---

## SUCCESS

Meaning:

```text
The step executed and returned exit code 0.
```

---

## FAILED

Meaning:

```text
The step executed and returned a non-zero exit code.
```

or:

```text
A required safety gate intentionally blocked execution.
```

---

## ERROR

Meaning:

```text
The orchestrator raised an exception while attempting to run the step.
```

Examples:

```text
module import failure
unexpected subprocess exception
environment issue
```

---

## SKIPPED

Meaning:

```text
The step was intentionally skipped.
```

Examples:

```text
module missing and skip_if_missing=True
optional future validation not available
```

## Zenput Safety Gate Interpretation

Command:

```bash
python -m scripts.run_zenput_pipeline --execute
```

Expected result:

```text
total_steps: 1
success: 0
dry_run: 0
skipped: 0
failed_or_error: 1
required_failed_or_error: 1

PIPELINE RESULT: FAILED
```

Expected step:

```text
00. [safety] Safety gate -> FAILED
```

Meaning:

```text
The wrapper blocked real execution because write-enabled Zenput legacy scripts require explicit --allow-legacy-writes.
```

This is correct and expected.

The failure protects:

```text
MySQL target zenput
legacy/zenput/last_run_timestamp.txt
existing Zenput refresh behaviour
```

This type of failure should be interpreted as successful safety behaviour when intentionally testing the gate.

---

## Zenput Full Legacy Execution Interpretation

Command:

```bash
python -m scripts.run_zenput_pipeline --execute --allow-legacy-writes
```

Current recommendation:

```text
Do not run casually.
Requires explicit operational approval.
```

Potential effects:

```text
legacy.zenput.zenput_mysql_forms may run
legacy.zenput.zenput_mysql_tasks may run
Zenput API may be called
MySQL target zenput may be written
form_templates may be inserted or updated
submissions may be inserted or updated
submission_answers may be deleted and reinserted for processed submissions
zenput_tasks may be inserted or updated
legacy/zenput/last_run_timestamp.txt may be updated
```

Before running this mode, review:

```text
docs/zenput-runbook.md
docs/zenput-legacy-assessment.md
```

and complete the controlled execution checklist in the Zenput runbook.

# How to Interpret Failures

## Required validation failure

If a required validator fails, the pipeline result should be:

```text
PIPELINE RESULT: FAILED
```

Investigate the failed validation name first.

---

## Missing table failure

Example:

```text
required_zenput_tables_exist: FAIL
```

Meaning:

```text
At least one expected Zenput table is missing.
```

Expected Zenput tables:

```text
form_templates
submissions
submission_answers
zenput_tasks
```

---

## Unmapped Zenput location failure

Example:

```text
zenput_location_mapping_available: FAIL
```

or:

```text
zenput_submissions_location_mapping: FAIL
```

Meaning:

```text
A submissions.location_name value exists in MySQL but is not configured in core/config/zenput.py.
```

Action:

```text
Review the new location.
Decide the correct company_source_key.
Update ZENPUT_LOCATION_SOURCE_KEY.
Rerun validators.
```

---

## Zenput-only classification failure

Example:

```text
zenput_only_locations_classified: FAIL
```

Meaning:

```text
Expected Zenput-only locations were not found or not classified correctly.
```

Current expected Zenput-only locations:

```text
León
Lindavista
Perisur
```

Action:

```text
Review core/config/zenput.py.
Confirm that ZENPUT_ONLY_LOCATIONS includes the expected company_source_key values.
Confirm that ZENPUT_LOCATION_SOURCE_KEY maps the location_name values correctly.
```

---

## Timestamp validation failure

Example:

```text
zenput_timestamp_file_valid: FAIL
```

Meaning:

```text
legacy/zenput/last_run_timestamp.txt is missing, empty, or not parseable.
```

Expected format:

```text
YYYY-MM-DDTHH:MM:SSZ
```

Example:

```text
2025-10-23T18:37:33Z
```

Important:

```text
Do not manually edit last_run_timestamp.txt unless the operational impact is understood.
```

---

## Safety gate failure

Example:

```text
Safety gate -> FAILED
PIPELINE RESULT: FAILED
```

This is expected when running:

```bash
python -m scripts.run_zenput_pipeline --execute
```

without:

```text
--allow-legacy-writes
```

Meaning:

```text
The pipeline prevented accidental execution of write-enabled legacy scripts.
```

This is correct safety behaviour.

# How to Identify Slow Steps

Review:

```text
duration_seconds
```

in the step-level results.

Common areas to monitor:

```text
Wansoft canonical load
Inventory bridge reports
Zenput legacy API extraction
Zenput output validation if table sizes grow
```

Do not change business logic only to reduce runtime.

Performance work should be reviewed separately from governance logic.

# Logs and Git

Logs should not be committed.

Before commit, run:

```bash
git status
```

Do not add:

```text
logs/
logs/purchases_pipeline_runs/
logs/inventory_pipeline_runs/
logs/zenput_pipeline_runs/
*.json
```

Recommended `.gitignore` entry:

```gitignore
# Pipeline run logs
logs/
```

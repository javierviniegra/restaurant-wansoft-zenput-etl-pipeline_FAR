# Pipeline Logging and Run Interpretation

## Purpose

This document explains how to read, interpret, and troubleshoot JSON pipeline run logs generated by the project orchestration scripts.

The goal is to make pipeline execution auditable and easy to diagnose.

This document applies to:

```text
Purchases pipeline
Inventory pipeline
Zenput safe wrapper
future orchestration scripts
```

Current implemented log folders:

```text
logs/purchases_pipeline_runs/
logs/inventory_pipeline_runs/
logs/zenput_pipeline_runs/
```

These logs are local execution artefacts.

They should not be committed.

Recommended `.gitignore` rule:

```gitignore
# Pipeline run logs
logs/
```

---

## Why Pipeline Logging Exists

Pipeline logging exists to answer:

```text
What pipeline ran?
When did it start?
When did it finish?
Did it run in dry-run mode?
Which steps executed?
Which steps were simulated?
Which steps succeeded?
Which steps failed?
Which steps were skipped?
How long did each step take?
Was the final required validation successful?
Was a safety gate triggered?
Did a real legacy execution modify data?
Did a validator detect a post-execution problem?
What run_id connects the console output to the JSON file?
```

The project uses JSON logs because they are:

```text
human-readable
machine-readable
easy to archive
easy to inspect after execution
easy to connect to future database run-log tables
```

# Common JSON Log Fields

Most pipeline logs include:

```text
run_id
pipeline_name
status
dry_run
started_at
finished_at
duration_seconds
total_steps
success
dry_run_steps
skipped
failed_or_error
required_failed_or_error
steps
```

Some fields vary by pipeline.

Purchases logs may not include every field that Inventory or Zenput logs include, depending on the current version of the script.

Inventory logs include:

```text
skipped
```

Zenput logs include additional execution and safety fields:

```text
execute
allow_legacy_writes
read_only
writes_database
writes_file
legacy
```

---

## Field: run_id

Example:

```text
run_id: 67fb593b-2bb4-43cf-94cb-fe319de4c92f
```

Purpose:

```text
Unique identifier for one pipeline execution.
```

Use this value to connect:

```text
console output
JSON log filename
future database run-log record
future validation results
```

---

## Field: pipeline_name

Possible current values:

```text
purchases_pipeline
inventory_pipeline
zenput_pipeline
```

Purpose:

```text
Identifies which pipeline generated the log.
```

---

## Field: status

Possible values:

```text
COMPLETED
FAILED
```

Meaning:

```text
COMPLETED:
    No required step failed.

FAILED:
    At least one required step failed or a safety gate blocked execution.
```

Important:

```text
FAILED is not always bad.
```

A failed safety gate can be expected and correct when testing protection behaviour.

A failed final validator can also be useful because it may detect that real ETL execution introduced or revealed a data condition that must be corrected before the pipeline is considered clean.

---

## Field: dry_run

Possible values:

```text
true
false
```

Meaning:

```text
true:
    Steps were simulated.
    Real ETL modules were not executed.
    No data writes should occur.

false:
    Steps may have executed for real, depending on the pipeline and flags.
```

---

## Field: execute

Used by:

```text
Zenput pipeline
```

Meaning:

```text
execute = true:
    The user requested real execution.

execute = false:
    The pipeline is running in default dry-run mode.
```

Important:

```text
execute = true does not necessarily mean legacy write steps executed.
```

For Zenput, write-enabled legacy steps require:

```text
--allow-legacy-writes
```

unless the run is:

```text
--execute --validation-only
```

---

## Field: allow_legacy_writes

Used by:

```text
Zenput pipeline
```

Meaning:

```text
allow_legacy_writes = true:
    Write-enabled legacy ETLs are allowed to run.

allow_legacy_writes = false:
    Write-enabled legacy ETLs must be blocked if present in the plan.
```

---

## Field: duration_seconds

Purpose:

```text
Shows how long the full pipeline execution took.
```

Use this to identify:

```text
unexpectedly slow runs
step runtime growth over time
possible performance bottlenecks
```

---

## Field: total_steps

Purpose:

```text
Counts how many steps were part of the executed or simulated plan.
```

Examples:

```text
Purchases pipeline:
    total_steps: 10

Inventory base pipeline:
    total_steps: 7

Inventory extended pipeline with bridge reports:
    total_steps: 10

Zenput default dry-run:
    total_steps: 4

Zenput validation-only execution:
    total_steps: 2

Zenput safety gate block:
    total_steps: 1
```

---

## Field: success

Purpose:

```text
Counts steps that executed and returned SUCCESS.
```

Important:

```text
In dry-run mode, success may be 0.
```

Example:

```text
success: 0
dry_run: 4
PIPELINE RESULT: COMPLETED
```

This is valid if the run was intentionally simulated.

---

## Field: dry_run_steps

Purpose:

```text
Counts steps marked as DRY_RUN.
```

This should equal `total_steps` in a full dry-run, unless a safety gate or skip condition changes the plan.

---

## Field: skipped

Purpose:

```text
Counts steps intentionally skipped.
```

A skipped step is not necessarily a failure.

Common reasons:

```text
optional future module not present
configured skip flag
future validator included but not available
```

---

## Field: failed_or_error

Purpose:

```text
Counts all steps with FAILED or ERROR status.
```

This includes required and optional steps.

---

## Field: required_failed_or_error

Purpose:

```text
Counts failed or errored steps that are required.
```

This is the most important summary field.

Rule:

```text
If required_failed_or_error > 0, the pipeline result should be FAILED.
```

---

## Step Status Values

Current status values:

```text
DRY_RUN
SUCCESS
FAILED
ERROR
SKIPPED
```

---

## DRY_RUN

Meaning:

```text
The step was simulated.
The module was not executed.
```

Valid for:

```text
safe planning
execution plan review
smoke tests
pipeline wrapper verification
```

---

## SUCCESS

Meaning:

```text
The step executed and returned exit code 0.
```

---

## FAILED

Meaning:

```text
The step executed and returned a non-zero exit code.
```

or:

```text
A required safety gate intentionally blocked execution.
```

or:

```text
A required validator detected a data condition that prevents the pipeline from being considered clean.
```

---

## ERROR

Meaning:

```text
The orchestrator raised an exception while attempting to run the step.
```

Examples:

```text
module import failure
unexpected subprocess exception
environment issue
```

---

## SKIPPED

Meaning:

```text
The step was intentionally skipped.
```

Examples:

```text
module missing and skip_if_missing=True
optional future validation not available
```

# Real Zenput Case: Legacy Steps Succeeded but Final Validator Failed

## Context

During the first controlled real legacy execution against the development/test database, the pipeline ran with:

```bash
python -m scripts.run_zenput_pipeline --execute --allow-legacy-writes
```

Initial result:

```text
01. Zenput location mapping validation -> SUCCESS
02. Zenput forms legacy ETL -> SUCCESS
03. Zenput tasks legacy ETL -> SUCCESS
04. Zenput output validation -> FAILED
```

Pipeline result:

```text
PIPELINE RESULT: FAILED
```

---

## Interpretation

This result means:

```text
The legacy ETL steps executed.
The development/test database was updated.
The final output validator found a data governance issue.
The pipeline correctly refused to mark the run as clean.
```

This is an important pattern:

```text
SUCCESS in ETL steps does not guarantee that the full pipeline is successful.
The final validator is the authority for whether the run can be accepted.
```

---

## Specific Failure

The output validator detected:

```text
unmapped_locations: ['Fonda Argentina Puebla']
```

That means:

```text
A new submissions.location_name value existed in MySQL after the real execution.
The value was not yet configured in core/config/zenput.py.
```

The new value was:

```text
Fonda Argentina Puebla
```

---

## Corrective Action

The correct action was to update:

```text
core/config/zenput.py
```

and add:

```python
"Fonda Argentina Puebla": "Puebla",
```

Puebla should not be added to:

```python
ZENPUT_ONLY_LOCATIONS
```

Reason:

```text
Puebla already exists as company_source_key.
Puebla is modeled as a future Odoo / operational branch.
Puebla should remain its own canonical key.
```

---

## Post-Correction Validation

After adding the Puebla mapping, these commands were run:

```bash
python -m py_compile core\config\zenput.py
python -m scripts.validate_zenput_location_mapping
python -m scripts.validate_zenput_outputs
python -m scripts.run_zenput_pipeline --execute --validation-only
```

Post-correction result:

```text
location mapping validator: PASSED
output validator: PASSED
validation-only pipeline: COMPLETED
```

Expected validation-only summary:

```text
total_steps: 2
success: 2
dry_run: 0
skipped: 0
failed_or_error: 0
required_failed_or_error: 0

PIPELINE RESULT: COMPLETED
```

---

## Operational Lesson

This case proves that the Zenput validation design is working.

The correct interpretation is:

```text
The first real execution was useful.
The post-load validator caught a real mapping gap.
The mapping gap was corrected centrally.
The corrected state now validates successfully.
```

The incorrect interpretation would be:

```text
The legacy ETLs succeeded, so the run is fully successful.
```

That is not sufficient.

For this project, the rule is:

```text
A pipeline is only clean when required validators pass.
```

# How to Interpret Failures

## Required validation failure

If a required validator fails, the pipeline result should be:

```text
PIPELINE RESULT: FAILED
```

Investigate the failed validation name first.

# Logs and Git

Logs should not be committed.

Before commit, run:

```bash
git status
```

Do not add:

```text
logs/
logs/purchases_pipeline_runs/
logs/inventory_pipeline_runs/
logs/zenput_pipeline_runs/
*.json
```

Recommended `.gitignore` entry:

```gitignore
# Pipeline run logs
logs/
```

If logs were accidentally staged:

```bash
git rm -r --cached logs/
```

Then confirm:

```bash
git status
```

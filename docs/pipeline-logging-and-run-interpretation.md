# Pipeline Logging and Run Interpretation

## Purpose

This document explains how to read and interpret pipeline execution logs generated by the project orchestration scripts.

The first implemented pipeline with JSON logging is:

```text
scripts/run_purchases_pipeline.py
```

Future inventory orchestration should follow the same logging pattern.

This document is intended to help operators, developers, and reviewers answer:

```text
Which pipeline was executed?
Was it a dry run or a real run?
Did the pipeline complete successfully?
Which step failed if something went wrong?
How long did each step take?
Where is the execution evidence stored?
What should be committed and what should remain local?
```

## Logging Design Principle

Pipeline logs are intended to provide execution traceability without changing the business logic of the ETL.

The logging layer should:

```text
record what ran
record when it ran
record whether it succeeded or failed
record how long each step took
record return codes
record error messages when available
avoid changing source data
avoid changing governance decisions
avoid writing to Odoo
```

The log is evidence of execution, not a governance decision record.

```text
logs/purchases_pipeline_runs/
```

Example:

```text
logs/purchases_pipeline_runs/20260722_120853_27ea21c9-9a4c-4abb-82b8-2334d06c422a.json
```

The filename contains:

```text
timestamp
run_id
```

Example structure:

```text
20260722_120853_27ea21c9-9a4c-4abb-82b8-2334d06c422a.json
```

Meaning:

```text
20260722_120853
    Local timestamp when the log file was generated.

27ea21c9-9a4c-4abb-82b8-2334d06c422a
    Unique run_id for that pipeline execution.
```

## Git Policy for Logs

Pipeline logs are local execution artefacts.

They should not be committed to Git.

Recommended `.gitignore` entry:

```gitignore
# Pipeline run logs
logs/
```

Reason:

```text
Logs may contain operational execution details.
Logs grow over time.
Logs are environment-specific.
Logs are useful locally but should not pollute the repository history.
```

If a log is needed for debugging, share only the relevant summary or attach it manually outside the normal Git workflow.

## Run ID

Each pipeline execution generates a unique:

```text
run_id
```

Example:

```text
27ea21c9-9a4c-4abb-82b8-2334d06c422a
```

The `run_id` is used to identify one specific execution.

The same `run_id` appears in:

```text
console output
JSON log filename
JSON log payload
```

Use the `run_id` when comparing a console output with its saved JSON log.

## Pipeline Log Structure

A pipeline log contains the following top-level fields:

```text
run_id
pipeline_name
status
dry_run
started_at
finished_at
duration_seconds
total_steps
success
dry_run_steps
failed_or_error
required_failed_or_error
steps
```

---

## Field Reference

### run_id

Unique identifier for the pipeline execution.

Example:

```json
"run_id": "27ea21c9-9a4c-4abb-82b8-2334d06c422a"
```

Use this to identify or discuss a specific run.

---

### pipeline_name

Name of the executed pipeline.

Current value for purchases:

```json
"pipeline_name": "purchases_pipeline"
```

Future inventory pipeline should use:

```json
"pipeline_name": "inventory_pipeline"
```

---

### status

Final pipeline status.

Expected values:

```text
COMPLETED
FAILED
```

Meaning:

```text
COMPLETED:
    No required step failed.

FAILED:
    At least one required step failed or returned an error.
```

Important:

```text
A pipeline can still show optional step failures if optional failure handling is enabled.
However, required_failed_or_error determines whether the full pipeline is failed.
```

---

### dry_run

Indicates whether the pipeline was simulated.

Expected values:

```text
true
false
```

Meaning:

```text
true:
    The pipeline printed the execution plan and simulated each step.
    No ETL modules were executed.

false:
    The pipeline executed the real ETL modules.
```

Use `dry_run = true` during validation of the orchestrator structure.

Use `dry_run = false` for real pipeline execution.

---

### started_at

Time when the pipeline started.

Example:

```json
"started_at": "2026-07-22 12:08:53"
```

---

### finished_at

Time when the pipeline finished.

Example:

```json
"finished_at": "2026-07-22 12:08:53"
```

---

### duration_seconds

Total runtime of the pipeline execution in seconds.

Example:

```json
"duration_seconds": 3604.44
```

Interpretation:

```text
Short duration:
    Usually dry-run or a small partial execution.

Long duration:
    Usually real execution that includes Wansoft canonical loading or heavy validation.
```

Current observation:

```text
The Wansoft canonical purchase load is the slowest step in the Purchases pipeline.
```

---

### total_steps

Total number of steps included in this pipeline execution.

Current Purchases pipeline after Step 13.4:

```json
"total_steps": 10
```

---

### success

Number of steps that completed successfully.

Example:

```json
"success": 10
```

For dry runs, this value is usually:

```text
0
```

because dry-run steps are counted separately as `dry_run_steps`.

---

### dry_run_steps

Number of steps simulated in dry-run mode.

Example:

```json
"dry_run_steps": 10
```

---

### failed_or_error

Number of steps with status:

```text
FAILED
ERROR
```

Example:

```json
"failed_or_error": 0
```

---

### required_failed_or_error

Number of required steps that failed or errored.

Example:

```json
"required_failed_or_error": 0
```

This is the most important failure indicator.

If this value is greater than zero:

```text
The pipeline result should be considered failed.
```

---

## Step-Level Log Structure

Each item in `steps` describes one pipeline step.

A step contains:

```text
step_id
name
module
group
required
status
started_at
finished_at
duration_seconds
return_code
error_message
```

---

## Step Field Reference

### step_id

Sequential identifier of the step.

Example:

```json
"step_id": "09"
```

Current Purchases pipeline order:

```text
01. Company source governance
02. Odoo purchase order and line ETL
03. Odoo purchase receipt ETL
04. Purchase inventory mapping backlog
05. Purchase backlog product reference report
06. Purchase company source eligibility
07. Odoo canonical purchase load
08. Wansoft purchase subsidiary mapping report
09. Wansoft canonical purchase load
10. Purchases canonical layer validation
```

---

### name

Human-readable step name.

Example:

```json
"name": "Wansoft canonical purchase load"
```

---

### module

Python module executed by the step.

Example:

```json
"module": "scripts.test_canonical_purchase_wansoft_etl"
```

The orchestrator executes steps using:

```bash
python -m <module>
```

---

### group

Logical category of the step.

Current Purchases groups:

```text
governance
odoo_snapshots
backlog
eligibility
canonical
wansoft
validation
```

Use `group` to understand which stage of the pipeline the step belongs to.

---

### required

Indicates whether the step is mandatory.

Expected values:

```text
true
false
```

Required steps stop the pipeline if they fail.

Optional steps may be allowed to fail depending on orchestration flags.

Current optional step:

```text
Purchase backlog product reference report
```

This step is diagnostic and does not promote products automatically.

---

### status

Step execution status.

Expected values:

```text
SUCCESS
FAILED
ERROR
DRY_RUN
```

Meaning:

```text
SUCCESS:
    The module executed and returned exit code 0.

FAILED:
    The module executed but returned a non-zero exit code.

ERROR:
    The orchestrator itself encountered an exception while trying to run the step.

DRY_RUN:
    The step was simulated and not executed.
```

---

### return_code

Process exit code returned by the executed module.

Common values:

```text
0:
    Success.

1 or other non-zero value:
    Failure.
```

For dry-run steps:

```text
return_code = null
```

---

### error_message

Contains an error message when a step fails or errors.

Expected value when successful:

```text
null
```

If a required step fails, review:

```text
error_message
return_code
console output around the failed step
```

---

## How to Read a Successful Run

A successful real run should show:

```text
status = COMPLETED
dry_run = false
failed_or_error = 0
required_failed_or_error = 0
```

Step-level status should show:

```text
SUCCESS
```

for all required steps.

Example summary:

```text
total_steps: 10
success: 10
dry_run: 0
failed_or_error: 0
required_failed_or_error: 0
PIPELINE RESULT: COMPLETED
```

---

## How to Read a Dry Run

A successful dry run should show:

```text
dry_run = true
dry_run_steps = total_steps
required_failed_or_error = 0
status = COMPLETED
```

Example summary:

```text
total_steps: 10
success: 0
dry_run: 10
failed_or_error: 0
required_failed_or_error: 0
PIPELINE RESULT: COMPLETED
```

A dry run validates orchestration structure only.

It does not validate database contents.

---

## How to Identify the Slowest Step

Open the JSON log and review:

```text
steps[*].duration_seconds
```

The step with the largest value is the slowest step.

For Purchases, the current expected slow step is usually:

```text
Wansoft canonical purchase load
```

Module:

```text
scripts.test_canonical_purchase_wansoft_etl
```

Reason:

```text
This step loads a large Wansoft historical dataset into canonical purchase tables.
```

Future optimisation should focus on:

```text
incremental refresh
date filters
batching strategy
index review
avoiding unnecessary full reloads
```

---

## How to Identify Failed Required Steps

Look for:

```json
"required": true,
"status": "FAILED"
```

or:

```json
"required": true,
"status": "ERROR"
```

If any required step failed:

```text
required_failed_or_error > 0
pipeline status = FAILED
```

The next action should be to inspect:

```text
step_id
name
module
return_code
error_message
console output
```

---

## How to Interpret Optional Step Failure

Optional steps are useful diagnostics but do not always need to stop the full pipeline.

Current optional step:

```text
Purchase backlog product reference report
```

If the optional step fails, review the issue, but do not assume the canonical layer is invalid unless the final validation step fails.

However, in current conservative mode, optional failures may still stop the pipeline unless the flag below is used:

```bash
--continue-on-optional-failure
```

## Canonical Validation Step

The final required validation step is:

```text
Purchases canonical layer validation
```

Module:

```text
scripts.validate_purchases_canonical_layer
```

This step validates:

```text
source-system coexistence
Antenas source split
Wansoft final-source companies
internal providers as vendors
internal providers not as final companies
canonical product mapping distribution
canonical table counts

```

The pipeline should not be considered successful unless this step passes.

## Rollout Company Pattern Validation

The canonical validation includes rollout-specific expectations.

Current rollout expectation types:

```text
migrated_from_wansoft
new_odoo_branch
```

---

### migrated_from_wansoft

Expected pattern:

```text
Odoo:
    final_odoo_enabled from operational_start_date onward

Wansoft:
    wansoft_history_before_odoo before operational_start_date
```

Not allowed:

```text
wansoft / final_wansoft_enabled
```

for the migrated company once the rollout is active.

Examples:

```text
Antenas
La Esquina Coyoacán
```

---

### new_odoo_branch

Expected pattern:

```text
Odoo:
    final_odoo_enabled
```

Not allowed:

```text
wansoft / final_wansoft_enabled
```

for the new Odoo branch once the rollout is active.

Examples:

```text
CentroMyJ
Puebla, when activated
```

---

### Active vs Inactive Rollout Expectations

Rollout expectations may be configured as:

```text
active = True
active = False
```

Meaning:

```text
active = True:
    validation is enforced and can fail the pipeline.

active = False:
    rollout is documented as future work but does not fail current validation.
```

Example:

```text
Puebla can be listed as a future new_odoo_branch with active = False.
```

When Puebla becomes active, change:

```text
active = False
```

to:

```text
active = True
```

and rerun the validation.

## Common Scenarios

### Scenario 1: Pipeline completed successfully

Indicators:

```text
status = COMPLETED
required_failed_or_error = 0
final validation = PASSED
```

Action:

```text
No immediate correction required.
Review any informational warnings or long-running steps.
```

---

### Scenario 2: Wansoft canonical load is slow

Indicators:

```text
Step 09 has the largest duration_seconds.
```

Action:

```text
Review whether full Wansoft reload is necessary.
Consider future incremental loading.
Review indexes and batch insert performance.
```

Do not change business logic only to reduce runtime.

---

### Scenario 3: Rollout company pattern fails

Indicators:

```text
rollout_company_patterns = FAIL
```

Action:

```text
Review COMPANY_SOURCE.
Review odoo_company_migration_policy.
Review whether the rollout expectation is active.
Review whether the company is migrated_from_wansoft or new_odoo_branch.
Reload source_system-specific canonical rows if policy changed.
```

If a company is not yet active, set:

```text
active = False
```

until rollout activation.

---

### Scenario 4: Internal providers appear as final companies

Indicators:

```text
internal_providers_not_as_companies = FAIL
```

Action:

```text
Review company mapping.
Confirm internal provider company names.
Confirm exclusion logic in canonical ETL.
```

Internal providers may appear as:

```text
vendor_name
```

but should not appear as final:

```text
company_name
```

---

### Scenario 5: Source-system coexistence fails

Indicators:

```text
source_system_coexistence = FAIL
```

Action:

```text
Confirm Odoo canonical load ran.
Confirm Wansoft canonical load ran.
Check source_system filters.
Check whether one source was deleted and not reloaded.
```
